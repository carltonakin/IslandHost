IIS supplies PORT through web.config; API_PORT=4000 and API_URL=http://127.0.0.1:4000 match this web build. A different API_URL requires rebuilding the web app on the trusted build machine.

HttpPlatformHandler starts node scripts/run.cjs start --iis-port with its assigned numeric port, which launches both API and web. Upload scripts/run.cjs before the updated web.config. 5. Give the application identity read/write access to `uploads/service-photos` or the configured SERVICE_UPLOAD_DIR. Follow [service photo setup and checks](service-photo-uploads.md). Confirm /login returns 200 and /api/health returns JSON 200. Unauthenticated /api/auth/me should return JSON 401; an empty same-origin POST to /api/auth/login should return JSON 400. Then sign in with the existing administrator and member credentials. Validate member/admin access boundaries and SMTP password recovery.
6. If the API path still returns a plain 500, inspect the private islandhost-node.log/provider-suffixed log after recycling. Configuration errors name the missing setting; API connection errors include safe codes. Keep the log private and configure rotation or disable temporary stdout logging after diagnosis.

For the already-uploaded build, upload scripts/run.cjs into the hosted scripts folder first, then upload the updated root web.config into the same folder as package.json and recycle the site. ## October 4 IIS port handoff update

The latest automatically generated hosting log reaches Nest initialization without a configuration error, but Next reports port 3000 and the public login and health requests time out. These observations suggest a port handoff problem; they do not prove the exact hosted configuration. The generated Next standalone server silently selects port 3000 if PORT is missing, zero, or nonnumeric (including an unexpanded IIS token).

The updated web.config passes the assigned port explicitly as `scripts/run.cjs start --iis-port %HTTP_PLATFORM_PORT%`. The launcher validates the expanded numeric value and supplies it as PORT to the web child, while preserving the API port. It logs `IslandHost ports: web=<assigned-port> source=IIS api=4000`. The number is assigned by IIS; do not hardcode it or assume it must differ from 3000. Invalid assignments now stop startup with a controlled error instead of silently selecting port 3000. Microsoft documents token expansion in arguments in the [HttpPlatformHandler configuration reference](https://learn.microsoft.com/en-us/iis/extensions/httpplatformhandler/httpplatformhandler-configuration-reference).

The patch archive `.runtime/releases/islandhost-iis-port-fix-20261004.zip` contains only web.config and scripts/run.cjs. Preserve their relative paths. Back up the hosted versions, upload the script first and web.config second, then recycle and open /api/health. If the fresh log lacks the new `IslandHost ports:` line, check that the files were uploaded into the application root actually launched by IIS. If it reports an invalid IIS assigned port, provide the safe error and hosted httpPlatform opening tag to diagnose the configuration. If it shows source=IIS but requests still hang, collect the subsequent private host log and ask the provider to check forwarding to that port.

Verification: `node --test --test-concurrency=1 tests/launcher.test.cjs` exercises the launcher with real concurrently/dotenv dependencies and isolated HTTP fixtures. These tests verify process port handoff and rejection of invalid values; they do not start the actual Next/Nest app or establish hosted SQL/SMTP readiness.
## Startup regression after the branding deployment

The owner reported that the site stopped responding after deploying the branding update. Direct public checks established successful HTTPS connections but no HTTP response from the login, API health, or logo paths within the probe timeouts. This is a subsequent outage; the earlier successful public checks above remain historical results.

A log confirmed by the owner as generated automatically after restarting the hosted website shows `npm start`, `IslandHost ports: web=3000 source=default api=4000`, and both child commands exiting with decimal code `3221225794`. The launcher did not receive the explicit IIS port argument or an inherited PORT. This startup invocation is inconsistent with the supplied root web.config, which starts node.exe directly with `scripts/run.cjs start --iis-port %HTTP_PLATFORM_PORT%`. The evidence does not establish whether the hosted file was replaced, a different application root is active, or a hosting startup override is being used.

Back up the hosted web.config and scripts/run.cjs, then restore both files from `.runtime/releases/islandhost-iis-port-fix-20261004.zip` into the application root used by IIS (the folder containing package.json). Upload scripts/run.cjs first and web.config second, or stop the site's pool during the replacement. Preserve the hosted private .env and the branded .next/standalone build. Restart the site's application pool and request /api/health. The new stdout log prefix is islandhost-node.log. Confirm `source=IIS`; the numeric web port is assigned by IIS and must not be hardcoded. If startup still runs through npm or says source=default, ask the host to confirm the site's physical application root and active startup configuration.

Decimal `3221225794` is hexadecimal `0xC0000142`, which Microsoft defines as `STATUS_DLL_INIT_FAILED`. This log does not name the DLL or prove the underlying cause. If it persists after restoring the intended startup and restarting, provide SmarterASP support with the fresh log and request the Windows application-event/HttpPlatformHandler startup details for the site's Node child processes. The port repair alone does not establish that the DLL failure is resolved. Updating npm is not a remedy established by this evidence.
